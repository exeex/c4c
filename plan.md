Status: Active

## Purpose

Turn the current pointer-local lowering follow-up into an execution runbook that
refreshes evidence, names the first owner, and repairs only the proven
prepared/RV64 pointer-local rule.

## Goal

Repair the current RV64 pointer-local route/runtime family for prepared
local-address, pointer-step, and store-source cases without reopening the older
idea 657 `loop-2e.c` representative route as the first owner.

## Core Rule

Use current semantic, prepared, RV64 route, object, disassembly, and runtime
facts to prove source, destination, and update order before changing lowering.
Do not match testcase names, fixed temporaries, local variable names, or final
assembly shape.

## Working Model

The active family has three route/runtime pairs:

1. loop-carried pointer postincrement
2. Duff fallthrough pointer-update producers
3. i16 local-array select/store

The first owner must be proven among prepared local-address publication,
pointer-step producer facts, store-source selection, and RV64 consumer
lowering. Implementation may start only after evidence identifies one of those
boundaries, or a smaller split is recorded with concrete proof.

## Execution Rules

- Keep routine progress and proof notes in `todo.md`.
- If the first owner splits into a different durable initiative, stop and ask
  the supervisor for lifecycle routing instead of broadening this plan.
- For each code-changing step, run build proof plus the supervisor-selected
  focused pointer-local subset. Broader backend regression belongs to the
  supervisor acceptance pass.
- Reject patches whose main effect is expectation churn, named-case matching,
  diagnostics-only relabeling, or preserving the same pointer-local failure
  behind a new helper name.

## Ordered Steps

### Step 1: Refresh Pointer-Local Evidence

Goal: Reproduce the current failure boundaries for all six focused rows.

Primary targets:

- `tests/backend/CMakeLists.txt`
- `tests/backend/case/riscv64_loop_carried_pointer_postincrement.c`
- `tests/backend/case/riscv64_duff_fallthrough_pointer_update_producers.c`
- `tests/backend/case/riscv64_i16_local_array_select_store.c`
- current prepared/RV64 dump, assembly, object, disassembly, and runtime
  artifacts generated by the focused tests

Actions:

- Run the focused route/runtime rows and collect the first failing diagnostic
  for each pair.
- Refresh semantic BIR and prepared-BIR evidence where the row's first failure
  does not already name the owner.
- Compare the loop-carried pair against the idea 657 representative pass so
  the route does not regress into the stale `loop-2e.c` owner.
- Record whether each row is owned first by prepared local-address
  publication, pointer-step producer facts, store-source selection, RV64
  consumer lowering, or a smaller split.

Completion check:

- `todo.md` records a focused evidence summary naming the first owner or split
  for every targeted row, with no implementation changes required for this
  step.

### Step 2: Select The First Repair Boundary

Goal: Choose one general pointer-local boundary for the first implementation
packet.

Primary targets:

- the prepared/RV64 producer or consumer surface proven by Step 1
- any focused backend case that can prove a positive shape and a fail-closed
  negative shape for that boundary

Actions:

- Select exactly one boundary from the Step 1 evidence.
- Define the positive and negative evidence the executor must preserve.
- If the six rows need separate owners, keep only the first owner in this
  runbook and record the separate owner candidates in `todo.md` for supervisor
  lifecycle routing.

Completion check:

- `todo.md` identifies one selected implementation boundary, the rows it owns,
  and the focused proof subset for the first repair packet.

### Step 3: Repair The Selected Pointer-Local Rule

Goal: Implement one general prepared/RV64 pointer-local rule that fixes or
fails closed at the proven owner.

Primary targets:

- the source files named by Step 1 and Step 2 evidence
- the focused backend route/runtime cases for the selected boundary

Actions:

- Repair publication or consumption of the proven pointer-local facts.
- Preserve explicit source, destination, and update-order ownership at the
  consumer program point.
- Add or update focused positive and negative tests only when they prove the
  general rule rather than the named baseline row.
- Keep rows outside the selected owner fail-closed with precise diagnostics.

Completion check:

- The selected focused route/runtime subset passes or fails closed at the
  proven owner.
- Build proof is fresh.
- No unrelated backend family changes are included.

### Step 4: Broaden Within The Pointer-Local Family

Goal: Prove that the repair did not regress nearby pointer-local rows and
decide whether another pointer-local packet remains.

Primary targets:

- all six current pointer-local rows
- idea 657 representative evidence as a nearby regression surface

Actions:

- Re-run the full six-row focused subset after the selected repair.
- Check whether remaining failures belong to the same selected owner, a
  separate pointer-local owner, or a non-pointer-local initiative.
- Record any remaining owner split in `todo.md` without mutating the source
  idea unless a separate initiative is required.

Completion check:

- `todo.md` records proof for all six rows and a clear next packet or close
  recommendation for the supervisor.

supervisor review.

Actions:
